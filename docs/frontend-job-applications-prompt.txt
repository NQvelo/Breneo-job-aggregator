FRONTEND — JOB APPLICATIONS (JOB AGGREGATOR URL ONLY)
======================================================

Use ONE public base URL for all job + application HTTP calls:

  NEXT_PUBLIC_JOB_AGGREGATOR_URL=https://breneo-job-aggregator.up.railway.app

Do NOT call breneo-api for apply / withdraw / my-applications.
Do NOT use Authorization: Bearer <jwt> on the job-aggregator — breneo JWTs are not
validated here (separate databases).

Login still happens in your app (breneo session / cookie / your auth layer). After login,
breneo-api must return signed application credentials (see §2). The frontend only talks
to the job-aggregator with those headers.

-------------------------------------------------------------------------------
1. TWO TYPES OF JOBS — TWO DIFFERENT APPLY BUTTONS (CRITICAL)
-------------------------------------------------------------------------------

Every job JSON from the aggregator includes:

  supports_in_app_apply: boolean
  apply_url: string | null
  platform: string

RULE — do not change fetched-job UX:

  IF job.supports_in_app_apply === true
     → platform is "employer" (posted by a company on Breneo)
     → Show your NEW in-app "Apply" button
     → POST /api/jobs/{id}/apply on the job-aggregator
     → Do NOT replace or remove apply_url in the model; you simply don't use it as the
       primary CTA for these jobs

  IF job.supports_in_app_apply === false
     → Job came from automatic fetch (greenhouse, lever, ashby, etc.)
     → Keep EXACTLY the same button/link behaviour as before
     → Use job.apply_url (external link, new tab, same label/styling you have today)
     → Do NOT call /api/jobs/{id}/apply for these jobs

Equivalent check: job.platform === "employer"  ⇔  supports_in_app_apply === true

Example (React):

  function JobApplyAction({ job, applicationAuth, onApplied }) {
    if (!job.supports_in_app_apply) {
      // Unchanged legacy behaviour
      return (
        <a href={job.apply_url} target="_blank" rel="noopener noreferrer">
          Apply
        </a>
      );
    }
    return (
      <BreneoApplyButton jobId={job.id} applicationAuth={applicationAuth} onApplied={onApplied} />
    );
  }

2. AUTH — SIGNED HEADERS (NOT BEARER)
-------------------------------------------------------------------------------

breneo-api and job-aggregator share env secret:

  APPLICATION_SIGNATURE_SECRET=<same value on both services>

On login (or GET /me), breneo-api returns something like:

  {
    "user": { "id": "550e8400-...", ... },
    "applicationAuth": {
      "userId": "550e8400-...",
      "timestamp": 1715952000,
      "signature": "<hex hmac>"
    }
  }

Signature algorithm (breneo-api must implement the same):

  message = f"{userId}:{timestamp}"
  signature = HMAC_SHA256(APPLICATION_SIGNATURE_SECRET, message).hexdigest()

Frontend stores applicationAuth in memory/context (refresh when breneo refreshes login).

On every application API call to the job-aggregator, send headers:

  X-Breneo-User-Id:     <applicationAuth.userId>
  X-Breneo-Timestamp:   <applicationAuth.timestamp>   (new timestamp when breneo re-signs)
  X-Breneo-Signature:   <applicationAuth.signature>

Optional: breneo can refresh signature when timestamp is older than ~15 minutes.

If headers are missing or invalid → 401 with envelope { success: false, message, error }.

Never put APPLICATION_SIGNATURE_SECRET in the browser.

4. API CLIENT (JOB AGGREGATOR ONLY)
-------------------------------------------------------------------------------

  const BASE = process.env.NEXT_PUBLIC_JOB_AGGREGATOR_URL!;

  type ApplicationAuth = {
    userId: string;
    timestamp: number;
    signature: string;
  };

  function applicationHeaders(auth: ApplicationAuth): HeadersInit {
    return {
      "Content-Type": "application/json",
      "X-Breneo-User-Id": auth.userId,
      "X-Breneo-Timestamp": String(auth.timestamp),
      "X-Breneo-Signature": auth.signature,
    };
  }

  async function aggregatorApply(
    jobId: number,
    auth: ApplicationAuth
  ) {
    const res = await fetch(`${BASE}/api/jobs/${jobId}/apply`, {
      method: "POST",
      headers: applicationHeaders(auth),
    });
    const json = await res.json();
    if (!json.success) throw new Error(json.message);
    return json.data;
  }

  async function getMyApplications(auth: ApplicationAuth, page = 1) {
    const res = await fetch(
      `${BASE}/api/users/me/applications?sort=-applied_at&page=${page}&limit=20`,
      { headers: applicationHeaders(auth) }
    );
    const json = await res.json();
    if (!json.success) throw new Error(json.message);
    return json.data;
  }

  async function withdrawApplication(jobId: number, auth: ApplicationAuth) {
    const res = await fetch(`${BASE}/api/jobs/${jobId}/application`, {
      method: "DELETE",
      headers: applicationHeaders(auth),
    });
    const json = await res.json();
    if (!json.success) throw new Error(json.message);
    return json.data;
  }

-------------------------------------------------------------------------------
5. ENDPOINTS (ALL ON JOB AGGREGATOR)
-------------------------------------------------------------------------------

5.1 Apply (employer jobs only)
  POST /api/jobs/{jobId}/apply
  Headers: X-Breneo-User-Id, X-Breneo-Timestamp, X-Breneo-Signature
  201 success | 400 employer_job_only (fetched job) | 409 already_applied | 401 auth

5.2 My applications
  GET /api/users/me/applications?sort=-applied_at&page=1&limit=20
  Same headers

5.3 Withdraw
  DELETE /api/jobs/{jobId}/application
  Same headers

5.4 Recruiter applicants (server route only — never browser)
  GET /api/jobs/{jobId}/applicants
  Header: X-Employer-Key: <secret from env, server-side only>

Use supports_in_app_apply from the response to branch UI.

-------------------------------------------------------------------------------
7. STATE MANAGEMENT SUGGESTION
-------------------------------------------------------------------------------

After login:
  - Save applicationAuth from breneo login/me response (not JWT for aggregator).

On job list/detail:
  - If supports_in_app_apply: optionally GET my-applications once and build Set(job_id).

On Apply click (employer jobs only):
  - POST apply with signed headers
  - On 409 → treat as already applied
  - On 400 employer_job_only → should not happen if UI branches correctly; fallback to apply_url

On Withdraw:
  - DELETE application, invalidate my-applications cache

10. MISTAKES TO AVOID
-------------------------------------------------------------------------------

  X  Authorization: Bearer on job-aggregator application routes
  X  Calling breneo-api URL for /api/jobs/.../apply
  X  In-app Apply on greenhouse/lever/ashby jobs (supports_in_app_apply === false)
  X  Changing external Apply link/button for fetched jobs
  X  Putting APPLICATION_SIGNATURE_SECRET in frontend env
  X  Sending only user_id without signature (will 401)
